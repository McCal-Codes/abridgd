# ADR-0006: Over-the-Air Updates via EAS Update

Last Updated: 2026-09-06

**Date:** 2026-09-06
**Status:** Proposed
**Deciders:** Engineering Lead
**Context:** Raised while unifying the iOS and Android release workflow (ADR follows [ADR-0005](0005-feed-pipeline-modularization.md))

---

## Context and Problem Statement

Every user-visible fix in Abridgd currently requires a full app store release. For a news reader this is a poor match for where the risk actually lives.

The app's failure surface is overwhelmingly JavaScript. It parses RSS from third-party publishers whose markup changes without warning, normalises HTML through `cheerio` and `node-html-parser`, and enriches articles through a remote AI service. A publisher changing their feed shape can break a whole category, and per [ADR-0005](0005-feed-pipeline-modularization.md) the feed pipeline is exactly the area under most active change. None of that is native code.

Today, fixing a one-line parser regression means: cut a release, wait for App Store review, and wait again for users to update. Readers see a broken Culture tab for days. The Android launch doubles the exposure, since a Play review runs on its own clock.

Meanwhile the native side is unusually stable. The app uses Continuous Native Generation — neither `ios/` nor `android/` is committed, and both are regenerated by `expo prebuild` from `app.json`. Native dependencies change rarely, and when they do it is deliberate.

That asymmetry — volatile JS, stable native — is precisely the shape over-the-air updates are designed for. The question is whether to adopt them, and if so under which runtime-versioning policy, because that choice determines whether OTA is a safety net or a way to brick installed apps.

Current state: `expo-updates` is not installed, and the generated manifest carries `expo.modules.updates.ENABLED = false`. Nothing needs to be undone; this is a greenfield decision.

## Decision Drivers

- **Time to fix a broken feed.** The dominant failure mode is JS-level and currently gated behind store review.
- **Blast radius control.** Any mechanism that ships code outside review must be able to stage and reverse a bad push.
- **Store compliance.** Must stay inside Apple and Google policy without ambiguity.
- **No new native surface.** The project deliberately keeps native config generated, not hand-maintained.
- **Debuggability.** A crash from an OTA-updated bundle must still produce a readable stack trace.
- **Cost proportional to scale.** The app is pre-launch on Android and small on iOS.

## Considered Options

### Option 1: Status quo — store releases only

**Description:** Keep shipping every change through App Store Connect and Play.

**Pros:**
- Zero new infrastructure, zero new dependencies, zero new failure modes.
- Every line users run has passed store review.
- No additional cost.

**Cons:**
- Bad, because a broken parser stays broken for days. This is the actual, recurring problem.
- Bad, because urgency pressure lands on release review rather than on the fix.
- Bad, because Android doubles the review latency once it launches.
- Bad, because it discourages small safe fixes — every fix costs a release.

### Option 2: EAS Update with the `appVersion` runtime policy

**Description:** Adopt `expo-updates`, deriving `runtimeVersion` from `app.json`'s `version` field (currently `1.5.0`).

**Pros:**
- Good, because the runtime version is human-readable and obviously tied to a release.
- Good, because it is trivial to reason about which binaries an update reaches.

**Cons:**
- Bad, because it is only safe if `version` is bumped whenever native code changes — and nothing enforces that. Adding a native dependency mid-cycle without a version bump would push an update to binaries that lack the native module, crashing on launch with no recourse but a store release.
- Bad, because this project's version bumps are a manual three-file ritual (`docs/process/release-process.md`), so the safety of every OTA push would rest on remembering to do it.
- Bad, because the failure is silent until it reaches users.

### Option 3: EAS Update with the `fingerprint` runtime policy

**Description:** Adopt `expo-updates` with `runtimeVersion: { policy: "fingerprint" }`. `@expo/fingerprint` hashes everything affecting the native runtime — dependencies, config plugins, `app.json` native keys — and updates only reach binaries with a matching hash.

**Pros:**
- Good, because native/JS compatibility is computed rather than remembered. Adding a native module changes the fingerprint, and the incompatible update simply is not offered.
- Good, because it fits Continuous Native Generation exactly: the native project is a pure function of `app.json` and `package.json`, which is what the fingerprint hashes.
- Good, because EAS already computes it — the Android preview build returned `fingerprint.hash` in its build metadata, so the infrastructure is live.
- Good, because it removes an entire class of human error from a mechanism that bypasses review.

**Cons:**
- Bad, because the runtime version is an opaque hash rather than a version string, so "which builds does this update reach?" needs tooling to answer.
- Bad, because it requires a new build more often — any native-affecting change cuts off older binaries from further updates. This is correct behaviour, but it is stricter than `appVersion`.

### Option 4: A third-party OTA service

**Description:** Use a non-Expo CodePush-style service.

**Pros:**
- Good, because it is nominally independent of the EAS platform.

**Cons:**
- Bad, because Microsoft retired App Center, which hosted the mainstream CodePush offering; the remaining paths are self-hosted or third-party.
- Bad, because it means operating update-distribution infrastructure to serve an app that already builds on EAS.
- Bad, because it duplicates a capability included with the platform the project already depends on.

## Decision Outcome

**Chosen option:** "Option 3 — EAS Update with the `fingerprint` runtime policy", because it addresses the real problem (slow JS fixes) while making the dangerous failure mode structurally impossible rather than merely documented.

The deciding argument against `appVersion` is that its safety depends on a manual step in a process that is already manual in three places. A mechanism that ships code around store review should not have a footgun whose trigger is forgetting to bump a number.

### Consequences

**Positive:**
- A broken feed parser can be fixed in minutes rather than days, on both platforms simultaneously.
- Fixes ship without consuming a release slot or a build number.
- Gradual rollouts (`--rollout-percentage`) allow exposing a risky parser change to 10% of readers first.
- A bad update can be reverted without a store submission.
- Android launches with the same safety net as iOS from day one.

**Negative:**
- A new runtime dependency (`expo-updates`) in the startup path — an update check on launch is a new thing that can fail, and must fail invisibly.
- Native-affecting changes now require builds more often, and older binaries stop receiving updates once the fingerprint moves.
- A second release channel to reason about: "is this fix in a build, an update, or both?"
- Sentry source maps must be uploaded per update or OTA crash reports become unreadable (see Implementation Notes — this interacts with a setting we changed recently).

**Neutral:**
- Cost is not a factor at current scale. The free tier covers 1,000 monthly active users with 100 GiB bandwidth; overage is $0.10/GiB. Worth revisiting if Android launch materially grows the user base.
- Store policy is settled: Apple permits downloaded JS executed by its own frameworks provided it does not change the app's primary purpose (the clause formerly cited as 3.3.2, now 3.3.1(B)); Google's position is comparable. Bug fixes, copy, and layout are unambiguously inside the line.

## Implementation Notes

Phased, so each phase is independently verifiable. This is not a one-commit change.

### Phase 1 — Wiring

```bash
npx expo install expo-updates
eas update:configure
```

`eas update:configure` writes `updates.url` and `runtimeVersion` into `app.json` and adds channel properties to `eas.json`'s build profiles. Set the policy explicitly rather than accepting a default:

```json
"runtimeVersion": { "policy": "fingerprint" }
```

Channels map onto the existing build profiles — `preview` → `preview`, `production` → `production`. The `development` profile should stay off any production channel so dev-client builds never pull production updates.

`index.ts` already calls `registerRootComponent`, which EAS Update requires for correct asset resolution. No change needed there.

### Phase 2 — Sentry source maps (do not skip)

This directly reverses a decision made in commit `0d41b0e`. That commit set `SENTRY_DISABLE_AUTO_UPLOAD=true` on the `preview` and `development` profiles to unblock the first Android build, which was correct at the time — internal test builds have no use for uploaded source maps.

Once OTA updates ship to real users, that reasoning inverts. Each published update carries a **different JS bundle** from the binary that runs it. Without per-update source maps, every crash in OTA-updated code arrives in Sentry as unreadable minified frames — and OTA-updated code is precisely the code most likely to be new and broken.

Required before any update reaches production:
- Source maps uploaded on `eas update`, not only on `eas build`.
- Sentry organisation and project configured. `@sentry/react-native/expo` currently warns `Missing config for organization, project` on every build; that warning becomes a real gap here.
- Keep the flag disabled for `development` only.

### Phase 3 — Runtime behaviour

Start with the default: check on load, download in the background, apply on next launch. Silent and unsurprising, and appropriate for a reader — nothing should yank the UI out from under someone mid-article.

Explicitly **not** doing on first pass: `fallbackToCacheTimeout > 0`, which blocks startup waiting on the network. A news app that hangs on a cold launch over bad cellular is worse than one running yesterday's bundle.

A later refinement, once the mechanism is trusted, is `useUpdates()` to surface a gentle "Update ready" affordance in Settings rather than waiting for an organic relaunch.

### Phase 4 — Operational practice

Document in `docs/process/release-process.md` as a distinct path from a release:

```bash
eas update --branch production --message "Fix Culture feed parser"
eas update --branch production --rollout-percentage 10   # stage risky changes
eas update:revert-update-rollout                          # reverse a bad push
```

The rule that keeps this honest: **an OTA update is for fixing what is broken, not for shipping what is new.** Features go through a release so they get review, a version number, and a changelog entry. Only one update can be rolled out on a branch at a time, so a staged rollout must be resolved before the next push.

### What OTA cannot fix

Worth stating plainly, because the boundary is not intuitive:

| Change | OTA? |
|---|---|
| Feed parser, HTML normalisation, AI prompt | Yes |
| Copy, styling, layout, navigation structure | Yes |
| Adding an Expo module (notifications, camera) | No — new build |
| Permissions, `app.json` native keys, config plugins | No — new build |
| Expo SDK upgrade | No — new build |
| App icon, splash screen | No — new build |

Anything in the "no" column changes the fingerprint, so an incompatible update is withheld rather than delivered. That is the policy working as intended.
